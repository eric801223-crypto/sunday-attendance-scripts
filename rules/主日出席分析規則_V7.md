## 執行方式（給 Claude）

### 程式來源（2026-11-14 使用者要求）

1. 優先從 GitHub 取得程式：儲存庫已設為公開（2026-11-15），直接執行 `git clone --depth 1 https://github.com/eric801223-crypto/sunday-attendance-scripts 程式資料夾`，用 cp 把需要的 .py 複製到工作目錄。程式內容不經過對話，不用 project_read 讀取，以節省用量並確保原封不動。clone 失敗時，若環境有 add_repo 工具，用它連上（owner：eric801223-crypto；repo：sunday-attendance-scripts；access：read）後再 clone 一次；沒有 add_repo 工具（例如排程）或呼叫失敗時，不影響第一次直接 clone 的嘗試。
2. 備援：clone 失敗（含上述重試）或缺少需要的檔案時，改用 project_read 讀取專案內同名 .py，原封不動存到工作目錄；並在回報中用一句話說明這次改用專案備援及原因（附錯誤訊息原文）。
3. 以下執行步驟中「讀取專案文件 `claude/xxx.py`，原封不動存到工作目錄」，一律依本節取得。互動版 HTML 的範本檔（`care_html_template.html`、`annual_html_template.html`）也依本節取得，與對應程式放在同一個資料夾。
4. 程式修改時（見執行步驟第10點），GitHub 與專案兩份都要更新：GitHub 用 add_repo（access：push）連上後 commit、push 到 main；專案用 project_write 存回同一個檔案。完成後重新 clone，用 cmp 確認 GitHub 上的檔案與存回專案的檔案逐位元組相同，再重跑回測確認通過。
5. 規則文件同步（2026-11-27 使用者要求）：GitHub 儲存庫的 `rules/` 資料夾存有規則文件副本（本文件、近一年出席分析規則_V1.md）及專案指示（專案指示.md）。規則文件修改時，GitHub 與專案兩份都要更新（GitHub 用 add_repo（access：push）連上後 commit、push 到 main；專案用 project_write），完成後重新 clone，用 cmp 確認兩份逐位元組相同。專案指示由使用者在 claude.ai 修改；修改後請 Claude 同步更新 GitHub 上的 `rules/專案指示.md`。

### 判斷分析模式

- 使用者只上傳一份點名報表 → **只有主日**模式，與 V6 相同。
- 使用者上傳三份點名報表（主日、小排、家聚會）→ **主日＋小排＋家聚會**模式。分類、順位、排序仍只依主日；另加＊標記與「主日沒來但有小排家聚會」內部名單。
- 三份報表的辨識：
  - 檔名慣例（2026-11-11 使用者約定）：檔名含 `churchday` 為主日、含 `group` 為小排、含 `home` 為家聚會。依此直接對應，不需詢問。
  - 檔名不符慣例時：
    - 主日報表為近12週出席總數最多的那一份（程式也會檢查，小排或家聚會總數不少於主日時停止）。
    - 中文檔名上傳後常變成底線，只能看出字數；2個字者為「小排」，5個字者為家聚會報表（2026-11-11 經使用者確認）。
    - 仍無法判斷時先問使用者，不自行猜測（小排與家聚會互換時，＊結果不變，但 Excel 次數欄會錯，回測也會失敗）。
- 只上傳兩份時，請使用者補齊第三份，或確認只做主日分析。

### 執行步驟

每次使用者上傳報表並要求分析時（報表應為一年期，例如2025年11月～2026年11月；不足一年時第9順位無法完整判定，程式會提示）：

1. 用 project_read 讀取專案文件 `claude/sunday_attendance.py`，原封不動存到工作目錄。
2. 把報表複製到獨立資料夾，執行：
   - 只有主日：`python3 -I sunday_attendance.py 主日報表.xlsx 輸出資料夾`
   - 三份報表：`python3 -I sunday_attendance.py 主日報表.xlsx 輸出資料夾 --group 小排報表.xlsx --home 家聚會報表.xlsx`
3. 若程式以「【停止】」結束（例如某週主日已過但全區出席為0、同一週有多個重複週次欄都有資料、三份報表製表日期不同、小排或家聚會報表缺少統計期間週次、或檔案疑似放錯），把訊息原文告訴使用者；全區出席為0者請他決定後再以 `--zero-week include` 或 `--zero-week exclude` 重跑，其餘請他確認後重新匯出；不自行判斷。
4. 正式輸出前回測：讀取專案文件 `claude/verify_lists.py`，以與分析時相同的參數執行（含 --zero-week、--group、--home）。此程式不引用分析程式，從原始報表重新計算，逐一核對姓名、所屬區、類別、類別說明行、排序、人數、「本週有出席」註記、＊標記、出席次數與矩陣，以及接近穩定名單、「主日沒來但有小排家聚會」名單（文字名單與 Excel 工作表）。
   - 顯示「【回測通過】」才可進行後續步驟。
   - 顯示「【回測失敗】」時，不製作卡片、不建立 Notion 項目、不製作 Notion 頁面 PDF、不製作互動版 HTML、不上傳 Google Drive（兩個資料夾都不上傳），把不符明細原文告訴使用者。
5. 製作手機轉發卡片與整合 PDF（每次都要做）：讀取專案文件 `claude/make_cards.py`，原封不動存到工作目錄，執行 `python3 -I make_cards.py 輸出資料夾/各區看望名單_YYYYMMDD.txt 卡片資料夾`。此程式只讀取已通過回測的文字名單（第一條「＝」分隔線以上），不重新計算；卡片完成後，同一支程式再把全部卡片依序號合成一份 PDF。內部名單（接近穩定、主日沒來但有小排家聚會）不製作卡片。
   - 顯示「【卡片完成】」才可上傳卡片；顯示「【PDF完成】」才可上傳 PDF。
   - 顯示「【卡片失敗】」或「【PDF失敗】」時，不上傳卡片與 PDF，把不符明細原文告訴使用者（Excel 與文字名單仍可上傳）。
6. 回報（2026-11-13 使用者要求）：最後回報只列連結，不重述摘要與數字（都在 Notion 頁面與 Drive 資料夾中）：
   - 「定期資料存放區」本次日期資料夾的連結。
   - Notion 關心名單頁的連結（同一次也做了近一年分析時，一併列近一年分析頁）。
   - 互動版 HTML 以 SendUserFile 傳送（見第11點），回報中不另外描述內容。
   - 只有出現「【停止】」、回測失敗、卡片或 PDF 失敗、HTML 失敗、Notion 核對不符、上傳失敗、登載示警、同名檔重複或其他需要使用者決定的事項時，才另外用幾句話說明。
7. 不用 SendUserFile 在對話中傳送檔案（2026-11-13 使用者要求）；全部檔案上傳 Google Drive（見第9點）。例外：互動版 HTML 每次都用 SendUserFile 傳送（2026-11-17 使用者要求，見第11點）。使用者另外指定要某個檔案時才傳送其他檔案。

## 一、統計期間與主日日期判定

1. 報表欄位日期為週一，主日實際日期＝報表日期＋6天（以日期函式計算，跨月、跨年、閏年2月29日均正確）。
2. 以報表內「製表日期」為基準，不依賴系統時間：只採用主日日期早於製表日期的週次（製表當天的主日不採用）。
3. 近12週內，主日日期已過但全區出席為0的週次，先停止並說明，由使用者決定是否計入。更早的週次（只用於第9順位）全區出席為0者，視為當週未點名，直接不納入。
4. 依實際日期排序，取最近12次已舉行的主日為統計期間。「近四週」指其中最後4次主日。「近一年內」指最近一次主日往前364天內、近12週以前的已舉行主日。
5. 每次輸出均列出採用的12次主日日期及未採用週次。
6. 重複週次欄：點名系統可能在跨年週匯出兩欄相同日期（例如2025-12-29兩欄，一欄全為0、一欄有資料）。同一週有多欄時，只有一欄有出席資料就採用該欄，並在週次說明寫「報表有重複週次欄，採用有出席資料的那一欄」；全部欄都為0時視為一週，依第3點處理；兩欄以上都有出席資料時停止，請使用者確認點名系統後重新匯出，不自行合併。

## 二、分析範圍

### 分區依據（每人只屬一區）

1. 「大區」為「會所青年區」→ 青年區。
2. 「大區」為「兒童專項」→ 兒童專項（不再計入1～7小區）。
3. 其餘依「小區」欄 → 1小區至7小區。
4. 欄位互相矛盾者依上列順序歸區，並列入「資料待確認」。

### 跨區名單（青職、大專）

「群組」欄為「青職」者另建青職跨區統計；「群組」欄為「大學」者另建大專跨區統計（2026-11-11 新增，名稱為「大專（跨區）」）。兩者都不重複計入全區人數，不論屬於哪一區（含青年區）都列入，因此同一人可能同時出現在所屬區名單與跨區名單。兩者都比照各區產出看望名單（文字名單最後兩段依序為青職、大專；Excel「青職」「大專」工作表），姓名後加註所屬區，例如「王○○（3小區）」。

### 排除名單（只記人數，不列姓名）

1. 姓名或欄位含「來訪」「訪客」「臨時」「福音朋友」者（例如社區訪客一、聖徒來訪1、福音朋友01），屬臨時點名用的非固定名單。
2. 最近12次主日完全未出席，且近一年內出席未達6次者（視為無效名單）。三份報表模式下，其中近一季小排或家聚會仍有紀錄者，另列「主日沒來但有小排家聚會」內部名單（見第五節）。

報表全部名單扣除上列兩類後，稱為「有效名單」。

## 四、看望順位

排序原則：先看平常出席程度（出席穩定 → 出席普通 → 總出席低），同一程度內，最近越有出席的人越優先。

| 順位 | 類別 | 白話說明 | 數字條件 |
| --- | --- | --- | --- |
| 1 | 出席穩定者本週缺席 | 往常固定來，這週沒來 | 12週來9次以上，上週有來、這週沒來 |
| 2 | 出席穩定者連續缺席兩週以上 | 往常固定來，但連續幾週沒來 | 12週來9次以上，已連續兩週以上沒來 |
| 3 | 出席普通者近期缺席 | 往常還算常來，最近一兩週沒來 | 12週來6～8次，最近一兩週沒來 |

| 6 | 總出席低，但最近一個月有來1次 | 原本不常來或是新人，最近一個月來了1次 | 前8週來0～4次，近4週來1次 |

## 五、小排、家聚會深入分析（只在三份報表模式）

1. 用途：找出「主日沒來、小排和家聚會也都沒有出現」的人，讓各區先找真正斷了接觸的人。分類、順位、排序與人數都不因此改變。
2. 期間：「近一季」與主日統計期間相同，即同樣12週（以報表週一欄位對應）；「近一個月」為其中最後4週。三份報表的製表日期必須相同。
3. 比對方式：以「姓名＋大區＋小區」比對；同區同名有多筆者，依名單順序第幾筆對應（三份報表由點名系統以相同名單順序匯出）。
   - 小排、家聚會報表都找不到此人：視為近一季無紀錄，標＊，並列入「資料待確認」。
   - 同區同名筆數在三份報表中不一致：無法比對，不標＊，列入「資料待確認」。
4. ＊標記：列入第1～9順位者，若近一季小排、家聚會都沒有出席紀錄，姓名前加「＊」（全形），例如「　＊王○○」，青職為「　＊王○○（3小區）」。
5. 主日沒來但有小排家聚會（內部名單，2026-11-12 起獨立，原 Excel「排除但仍有接觸」工作表）：
   - 對象：主日近12週0次且近一年內未達6次而被排除者中，近一季小排或家聚會有紀錄的人。這些人不在關心名單上，但仍有連結，可邀請來主日。
   - 與關心名單分開，不製作卡片、不放入 PDF。
